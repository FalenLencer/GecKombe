Architecture du firmware

WSPCAMQ9

Le firmware tourne sur l'ESP32-S3 en USB natif (CDC). La boucle principale gère le réseau en permanence. Les fonctions de marche utilisent setPWM() — envoi immédiat sans interpolation — suivi d'un waitMove() non-bloquant qui maintient le WebSocket vivant pendant l'attente. Deux setPWM() consécutifs sur la même paire diagonale sont envoyés en ~600 µs d'écart naturel I²C, ce qui les rend quasi-simultanés.

Le robot pilote 12 servos : 8 servos de mouvement (hanches + genoux, ch0–ch7) et 4 rotules de hanche (ch8–ch11) maintenues en position fixe de contre-couple.

PCA

Toutes les positions sont calibrées individuellement par canal, car les servos sont montés à des angles différents selon la patte. Les valeurs en ticks correspondent à des impulsions PWM à 50 Hz sur un PCA9685 à 25 MHz d'oscillateur.

Conversion ticks ↔ degrés
Servo GX3270BLS 270° : 102 ticks = 500 µs = 0° · 307 ticks = 1500 µs = 135° · 512 ticks = 2500 µs = 270°
1 tick ≈ 0.659°. Les limites mécaniques mesurées sur le robot sont différentes selon chaque canal.

C++Helpers hanche — direction mécanique intégrée
// ch0 BR et ch4 FR : montés inversés → avancer = +delta
static inline uint16_t hipBR(int delta) {
  return (uint16_t)constrain(HOME_BR_HIP + delta, LIM_BR_HIP_MIN, LIM_BR_HIP_MAX);
}
// ch2 BL et ch6 FL : sens normal → avancer = −delta
static inline uint16_t hipBL(int delta) {
  return (uint16_t)constrain(HOME_BL_HIP - delta, LIM_BL_HIP_MIN, LIM_BL_HIP_MAX);
}
static inline uint16_t hipFR(int delta) {
  return (uint16_t)constrain(HOME_FR_HIP + delta, LIM_FR_HIP_MIN, LIM_FR_HIP_MAX);
}
static inline uint16_t hipFL(int delta) {
  return (uint16_t)constrain(HOME_FL_HIP - delta, LIM_FL_HIP_MIN, LIM_FL_HIP_MAX);
}
Pourquoi BR et FR sont "inversés" ?
Les servos de droite sont montés en miroir des servos de gauche pour des raisons mécaniques. Pour que toutes les pattes avancent dans la même direction, les hanches droites (ch0, ch4) augmentent leurs ticks quand elles avancent, tandis que les hanches gauches (ch2, ch6) les diminuent. Les helpers hipBR/BL/FR/FL() absorbent cette asymétrie — le reste du code utilise simplement +HIP_STEP pour avancer et -HIP_STEP pour reculer.

Initialisation — setup()

WSPCANET

Exécutée une seule fois au boot. Elle affiche la raison du reset (brownout, panic, watchdog), initialise le PCA9685 avec les bons paramètres d'oscillateur, puis envoie les 12 servos en position home un par un avec 300 ms d'écart pour éviter les pics de courant.

C++setup() — séquence d'initialisation
void setup() {
  Serial.begin(115200);
  delay(300);

  // Affiche la raison du dernier reset — utile pour diagnostiquer les brownouts
  esp_reset_reason_t r = esp_reset_reason();
  if (r == ESP_RST_BROWNOUT) Serial.print(" *** BROWNOUT ***");

  // ── GPIO MQ-9 ─────────────────────────────────────────────────────────
  // GPIO4 = ADC (compatible WiFi sur ESP32-S3, pas de restriction ADC2)
  // GPIO5 = seuil digital du comparateur interne du module
  pinMode(MQ9_ANALOG_PIN,  INPUT);
  pinMode(MQ9_DIGITAL_PIN, INPUT);
  memset(servoPos, 0xFF, sizeof(servoPos));

  // ── I²C + PCA9685 ────────────────────────────────────────────────────
  // SDA=GPIO8, SCL=GPIO9 (PCB custom)
  // Oscillateur 25 MHz = valeur correcte datasheet NXP PCA9685
  // IMPORTANT : 27 MHz (valeur incorrecte souvent utilisée) faussait
  // tous les timings PWM et causait les tremblements initiaux
  Wire.begin(I2C_SDA, I2C_SCL);
  Wire.setClock(100000);
  pca.begin();
  pca.setOscillatorFrequency(25000000);
  pca.setPWMFreq(50);
  delay(150);

  // ── Init servos séquentielle — un par un, 300 ms d'écart ─────────────
  // Évite les pics de courant qui causaient les brownouts de l'ESP32 original.
  // sendServo() = setPWM() + waitMove(300)
  sendServo(CH_BR_HIP,  HOME_BR_HIP);  sendServo(CH_BR_KNEE, TENDU_BR);
  sendServo(CH_BL_HIP,  HOME_BL_HIP);  sendServo(CH_BL_KNEE, TENDU_BL);
  sendServo(CH_FR_HIP,  HOME_FR_HIP);  sendServo(CH_FR_KNEE, TENDU_FR);
  sendServo(CH_FL_HIP,  HOME_FL_HIP);  sendServo(CH_FL_KNEE, TENDU_FL);
  // Rotules : contre-couple fixe
  sendServo(CH_BR_BALL, BALL_BR);  sendServo(CH_BL_BALL, BALL_BL);
  sendServo(CH_FR_BALL, BALL_FR);  sendServo(CH_FL_BALL, BALL_FL);

  // ── WiFi + serveurs ───────────────────────────────────────────────────
  WiFi.begin(SSID, PASSWORD);
  // HTTP port 80 + WebSocket port 81
  httpServer.begin();
  wsServer.begin();
  wsServer.onEvent(onWsEvent);
}
Oscillateur PCA9685 — erreur critique corrigée
L'oscillateur interne du PCA9685 est de 25 MHz (datasheet NXP). Utiliser 27 MHz — comme dans les versions précédentes — faussait tous les timings PWM : le PCA générait ~54 Hz au lieu de 50 Hz, les impulsions étaient ~8% trop longues, les servos partaient en butée et consommaient 2–3 A en permanence même à l'arrêt.

Boucle principale — loop()

WSPCAMQ9

Pompe le réseau à chaque tour, détecte les transitions de commande, et appelle la fonction de marche correspondante. La détection de transition permet d'appeler standStill() exactement une fois au passage à CMD_STOP, sans l'appeler en boucle à chaque tour de loop().

C++loop() — gestion des transitions et démarche
void loop() {
  httpServer.handleClient();
  wsServer.loop();

  // Copie atomique de la commande volatile
  Command cmd = pendingCmd;

  // Détection de transition — agit UNE SEULE FOIS au changement de commande
  if (cmd != currentCmd) {
    if (cmd == CMD_STOP && wasMoving) {
      standStill();
      wasMoving = false;
    }
    currentCmd = cmd;
    gaitStep = 0;   // Repart du début du cycle à chaque nouvelle commande
  }

  switch (currentCmd) {
    case CMD_FORWARD:  wasMoving = true; walkForward();  break;
    case CMD_BACKWARD: wasMoving = true; walkBackward(); break;
    case CMD_STOP:
    default: break;
  }

  // MQ-9 toutes les 2 s — diffusé à tous les clients connectés
  if (millis() - lastSensorMs > 2000) {
    lastSensorMs = millis();
    SensorData d = readMQ9();
    // ... sérialisation JSON + broadcastTXT()
  }
}
Fonctions de marche semi-bloquantes
Chaque phase de marche contient un waitMove(ms) qui bloque pendant ms millisecondes. Pendant cette attente, wsServer.loop() et httpServer.handleClient() sont appelés toutes les 5 ms pour garder la connexion WebSocket vivante. Le MQ-9 est donc lu régulièrement seulement quand le robot est à l'arrêt.

Réception des commandes — onWsEvent()

WebSocket entrant

Callback déclenché par la librairie WebSocketsServer à chaque message. Gère trois types de messages : ping (latence), cmd (déplacement), et cal (calibration manuelle). À la déconnexion, force CMD_STOP par sécurité.

C++onWsEvent() — trois types de messages
// ── Ping de latence ────────────────────────────────────────────────────
// {"type":"ping"} → réponse immédiate {"type":"pong"}
// Le dashboard mesure l'aller-retour pour afficher la latence en ms
if (strcmp(t, "ping") == 0) {
  wsServer.sendTXT(num, "{\"type\":\"pong\"}");
  return;
}

// ── Commande de déplacement ────────────────────────────────────────────
// {"type":"cmd", "cmd":"forward", "speed":50}
// La vitesse (0–100) contrôle moveMs() → durée de chaque phase de marche
if (strcmp(t, "cmd") == 0) {
  if (doc.containsKey("speed"))
    speedPct = (uint8_t)constrain((int)doc["speed"], 0, 100);
  // Mise à jour de pendingCmd — lu par loop() à son prochain tour
  if (next != pendingCmd) gaitStep = 0;
  pendingCmd = next;
}

// ── Calibration individuelle par canal ────────────────────────────────
// {"type":"cal", "ch":4, "ticks":280}
// Plage autorisée : 0–600 (élargie pour trouver les butées mécaniques)
// Utilisé par calibration.html — envoie immédiatement sans attente
if (strcmp(t, "cal") == 0) {
  uint8_t  ch    = (uint8_t)(int)doc["ch"];
  uint16_t ticks = (uint16_t)constrain((int)doc["ticks"], 0, 600);
  pca.setPWM(ch, 0, ticks);
  servoPos[ch] = ticks;
}
Calibration en live depuis le navigateur
Le message cal permet d'ajuster n'importe lequel des 12 canaux en temps réel depuis calibration.html. La plage 0–600 ticks est volontairement plus large que les limites mécaniques pour permettre de trouver les vraies butées. Pendant la marche, les fonctions hipBR/BL/FR/FL() appliquent elles les limites mécaniques strictes via constrain().

Envoi direct — setPWM()

PCA9685 PWM

Envoie une commande PWM immédiatement au PCA9685, sans aucune attente. Utilisée pour commander plusieurs servos quasi-simultanément : deux appels consécutifs sont séparés de ~600 µs seulement (délai naturel I²C), ce qui est suffisamment rapide pour que les deux membres d'une paire diagonale démarrent ensemble.

C++setPWM() — envoi immédiat, mémorise la position
void setPWM(uint8_t ch, uint16_t ticks) {
  if (ch >= 16) return;
  ticks = (uint16_t)constrain((int)ticks, 0, 600);
  servoPos[ch] = ticks;      // Mémorise pour éviter les re-écritures inutiles
  pca.setPWM(ch, 0, ticks);   // Envoie immédiatement sur le bus I²C
}

Attente non-bloquante — waitMove()

PCA9685WS

Attend ms millisecondes tout en continuant à pomper le réseau toutes les 5 ms. C'est le mécanisme qui permet d'attendre que les servos atteignent leur cible sans déconnecter le WebSocket.

C++waitMove() — boucle d'attente avec pompage réseau
void waitMove(unsigned long ms) {
  unsigned long t0 = millis();
  while (millis() - t0 < ms) {
    wsServer.loop();           // Maintient le WebSocket vivant
    httpServer.handleClient(); // Répond aux requêtes HTTP pendant l'attente
    delay(5);
  }
}
Durée par phase selon la vitesse
moveMs() calcule la durée en fonction de speedPct : speed=0 → 800 ms/phase · speed=100 → 300 ms/phase. Un cycle complet (4 phases) dure donc de 1.2 s (rapide) à 3.2 s (lent). Les GX3270BLS atteignent 60° en ~130 ms à 6.6V — 300 ms est largement suffisant pour tout déplacement utile.

Envoi avec attente — sendServo()

PCA9685

Utilisée uniquement pour l'initialisation et standStill() : envoie une commande et attend 300 ms que le servo arrive à sa position. Ne convient pas à la marche (trop lente pour commander plusieurs servos à la fois).

C++sendServo() — envoi + attente 300 ms
void sendServo(uint8_t ch, uint16_t ticks) {
  setPWM(ch, ticks);
  waitMove(300);
}

Posture debout — standStill()

PCA9685

Ramène tous les servos en position home de façon séquentielle et sécurisée. L'ordre en 3 phases évite les à-coups : d'abord les genoux à mi-course (ni pliés ni tendus), puis les hanches au centre, puis les genoux en position tendue. Appelée une seule fois à la transition vers CMD_STOP.

C++standStill() — retour home en 3 phases sécurisées
void standStill() {
  gaitStep = 0;

  // Phase 1 : genoux à mi-course — évite les mouvements brusques
  // depuis une position de patte potentiellement levée
  sendServo(CH_BR_KNEE, (TENDU_BR + PLIE_BR) / 2);
  sendServo(CH_BL_KNEE, (TENDU_BL + PLIE_BL) / 2);
  sendServo(CH_FR_KNEE, (TENDU_FR + PLIE_FR) / 2);
  sendServo(CH_FL_KNEE, (TENDU_FL + PLIE_FL) / 2);

  // Phase 2 : hanches au centre
  sendServo(CH_BR_HIP, HOME_BR_HIP);
  sendServo(CH_BL_HIP, HOME_BL_HIP);
  sendServo(CH_FR_HIP, HOME_FR_HIP);
  sendServo(CH_FL_HIP, HOME_FL_HIP);

  // Phase 3 : genoux tendus — robot posé sur ses 4 pattes
  sendServo(CH_BR_KNEE, TENDU_BR);
  sendServo(CH_BL_KNEE, TENDU_BL);
  sendServo(CH_FR_KNEE, TENDU_FR);
  sendServo(CH_FL_KNEE, TENDU_FL);
}

Trot diagonal — walkForward()

PCA9685

Exécute un cycle de trot diagonal vers l'avant en 4 phases. La clé est que les deux membres d'une paire bougent ensemble : deux setPWM() consécutifs (genou + hanche) sont envoyés sans attente entre eux, puis un seul waitMove() laisse les 4 servos de la paire atteindre leur cible simultanément.

Paire A = FR (avant droit) + BL (arrière gauche) Paire B = FL (avant gauche) + BR (arrière droit) Phase 0 Phase 1 Phase 2 Phase 3 ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ A lève │ │ A pose │ │ B lève │ │ B pose │ │ et avance│ │ B pousse │ │ et avance│ │ A pousse │ │ B au sol │ │ (propul) │ │ A au sol │ │ (propul) │ └──────────┘ └──────────┘ └──────────┘ └──────────┘ 4 setPWM() 4 setPWM() 4 setPWM() 4 setPWM() waitMove(ms) waitMove(ms) waitMove(ms) waitMove(ms)
C++walkForward() — trot diagonal, 4 phases
void walkForward() {
  unsigned long ms = moveMs();   // 300–800 ms selon speedPct

  switch (gaitStep) {

    case 0:
      // Paire A (FR+BL) : lever ET avancer simultanément
      // 4 setPWM() envoyés en ~2.4 ms au total (délai I²C naturel)
      // puis un seul waitMove() pour les laisser tous arriver
      setPWM(CH_FR_KNEE, PLIE_FR);           // FR genou plié
      setPWM(CH_FR_HIP,  hipFR(+HIP_STEP));   // FR hanche avance
      setPWM(CH_BL_KNEE, PLIE_BL);           // BL genou plié
      setPWM(CH_BL_HIP,  hipBL(+HIP_STEP));   // BL hanche avance
      waitMove(ms);
      break;

    case 1:
      // Paire A pose + Paire B pousse (propulsion vers l'arrière)
      setPWM(CH_FR_KNEE, TENDU_FR);           // FR pose
      setPWM(CH_BL_KNEE, TENDU_BL);           // BL pose
      setPWM(CH_FL_HIP,  hipFL(-HIP_STEP));   // FL pousse arrière
      setPWM(CH_BR_HIP,  hipBR(-HIP_STEP));   // BR pousse arrière
      waitMove(ms);
      break;

    case 2:
      // Paire B (FL+BR) : lever ET avancer simultanément
      setPWM(CH_FL_KNEE, PLIE_FL);
      setPWM(CH_FL_HIP,  hipFL(+HIP_STEP));
      setPWM(CH_BR_KNEE, PLIE_BR);
      setPWM(CH_BR_HIP,  hipBR(+HIP_STEP));
      waitMove(ms);
      break;

    case 3:
      // Paire B pose + Paire A pousse
      setPWM(CH_FL_KNEE, TENDU_FL);
      setPWM(CH_BR_KNEE, TENDU_BR);
      setPWM(CH_FR_HIP,  hipFR(-HIP_STEP));
      setPWM(CH_BL_HIP,  hipBL(-HIP_STEP));
      waitMove(ms);
      break;
  }
  gaitStep = (gaitStep + 1) % 4;
}
Pourquoi genou ET hanche en même temps ?
Dans les versions précédentes, le genou et la hanche bougeaient séparément (genou d'abord, puis hanche), ce qui donnait un mouvement saccadé peu naturel. En les commandant ensemble — genou plié + hanche avancée dans la même phase — la patte décrit une trajectoire courbe plus naturelle et le robot avance réellement au lieu de juste balancer ses membres.

PCA9685

Même structure en 4 phases que walkForward(), mais les deltas de hanche sont inversés : +HIP_STEP devient -HIP_STEP et vice versa. Les genoux plient et tendent dans le même ordre.

Capteur gaz — readMQ9()

MQ-9 ADC

Lit les deux sorties du module MQ-9 et calcule une estimation en ppm de CO via la loi puissance log-log de la datasheet. Sur ESP32-S3, l'ADC2 est utilisable avec le WiFi actif (contrairement à l'ESP32 classique).

C++readMQ9() — lecture ADC + calcul ppm CO
SensorData readMQ9() {
  SensorData d;
  d.raw   = analogRead(MQ9_ANALOG_PIN);     // 0–4095, GPIO4
  d.alert = (digitalRead(MQ9_DIGITAL_PIN) == LOW); // GPIO5

  d.voltage = (d.raw / ADC_MAX) * VCC_V;   // 0–3.3 V

  // RS = résistance interne du capteur (pont diviseur avec RL=10kΩ)
  d.rs = (d.voltage > 0.01f) ? RL_VALUE * (VCC_V - d.voltage) / d.voltage : 0.0f;

  // ratio RS/RO — entrée de la courbe datasheet (RO = résistance en air pur)
  d.ratio = (RO > 0.0f) ? d.rs / RO : 0.0f;

  // Loi puissance datasheet MQ-9 pour le CO : ppm = 599.65 × (RS/RO)^−2.244
  d.ppm = (d.ratio > 0.0f) ? 599.65f * powf(d.ratio, -2.244f) : 0.0f;

  return d;
}
Calibration RO obligatoire
La constante RO = 10.0 est la résistance du capteur en air pur. Elle varie d'un module à l'autre. Pour calibrer : laissez chauffer 5 minutes en air pur, relevez la valeur de rs dans le moniteur série, et remplacez RO par cette valeur. Sans calibration, les ppm sont indicatives uniquement.
